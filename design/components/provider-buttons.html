Provider sign-in buttons

The only way into PinVoyager. Four providers, one shared geometry, four mandated skins.

These are the one place in the design system where house style does not win. Google and Apple both publish binding branding requirements — exact wordmark, minimum size, permitted color variants, and required clear space. Non-compliance is grounds for rejection during provider app review, which blocks launch. Treat changes here as a correctness question, not a taste question, and check the current published guidelines before altering anything.

The set

All four share a height, a corner radius, an icon size, and the label grammar "Continue with X" — so the sign-in screen reads as one set of equivalent choices rather than four vendors competing for attention. Order is by expected usage.

On a dark surface

Google and Microsoft keep their light treatment in dark mode. Both providers permit a dark variant, but a dark Google button next to a black Apple button becomes hard to tell apart at a glance — brand recognition is the entire reason these buttons look the way they do, so preserving distinguishability wins.

Note the hairline outline on the black Apple button against near-black. Without it the button's edge disappears entirely, which is exactly the non-text contrast problem the border tokens exist to prevent.

Implementation notes for phase 3

ProviderProtocolWatch for
GoogleOIDC Straightforward. Standard discovery document, standard JWKS.
MicrosoftOIDC Tenant configuration decides who can sign in — the common endpoint accepts both personal and work accounts.
AppleOIDC, with deviations The awkward one — build it first. Callback is a form_post, so it is a POST with a form body rather than a GET with query parameters. The client secret is a JWT you generate and sign yourself, and it expires (six months maximum). The user's name arrives only on first authorization and never again.
FacebookOAuth2 — not OIDC There is no ID token to verify. Exchange the code, then call the Graph API, and use the app-scoped ID as the subject. Do not attempt ID token validation.
