Flows

Upload pipeline

From file selection to a photo placed on a map. Most of this diagram is rejection paths, which is the correct proportion — an upload endpoint that accepts arbitrary bytes from the internet is the most exposed surface in the product.

Two branches here are load-bearing and easy to skip. The variant re-encode must strip all metadata, or the granularity feature is decorative and leaks exact GPS to anyone who downloads a file. And the no-GPS branch is not an error case — it is the normal outcome for screenshots, scans, and any camera with location services off.

Ingest and validation

1Validation is ordered cheapest-first. Size cap before body read, magic bytes before decode, dimensions before full decode. Each gate is there so the expensive operation behind it never runs on hostile input.
2Content-addressed paths remove path traversal as a category. No user-supplied string ever reaches the filesystem, so there is no ../ to defend against.
3Deduplication requires reference counting. Two users can upload identical bytes and share one file — so deleting one photo must not remove the file another photo still points at.

Placement — including the no-GPS branch

4Rounding must be stable. Reading the same photo twice returns identical coordinates. Re-sampling per request makes pins jitter between loads and — worse — lets repeated observation average the noise away, recovering the true position.
5Where granularity is applied is an open question with a deadline. Rounding at read time keeps exact coordinates in the database but allows the precision to be loosened later; rounding at ingest discards them permanently. It has to be decided before real data exists, because it is not reversible afterwards.
6Stale GPS fixes happen. A camera holding a fix from a previous city will place a photo hundreds of kilometres away with full confidence. The review step exists so the user sees this before publishing rather than after.

Serving — never from disk directly

7The failure mode being avoided is a stored XSS. A user uploads a file the browser sniffs as HTML, it is served from our origin, and it executes against another user's session. The magic-byte check and these response headers are the two defences, and both require a handler in the path.
