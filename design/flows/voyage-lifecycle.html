Flows

Voyage lifecycle

Create, populate, publish, edit, delete. The draft state exists so a voyage is not world-readable the instant it is created and half-populated.

There are exactly two states, and one boundary that matters. Draft is visible only to its owner and returns 404 to everyone else. Published is visible to the entire internet, signed in or not. Everything interesting in this diagram happens at the crossing between them.

Create through publish

1A draft returns 404, not 403. "Forbidden" would confirm that a voyage exists at that address, allowing unpublished work to be enumerated by probing IDs.
2Granularity is enforced at the serialization boundary, once. A response type that cannot be constructed without applying it is worth the extra type machinery, because per-endpoint enforcement fails the first time someone adds an endpoint and forgets.
3Unpublishing is real and reversible. It returns the voyage to draft rather than deleting it, which is what most people actually want when they have second thoughts about something public.

Deletion

4Deleting a voyage does not delete its photographs. They return to the library. Saying so in the confirmation is why people are willing to clean up dead drafts instead of leaving them forever.
5Account deletion interacts with content-addressed deduplication. Two users uploading identical bytes share one file on disk, so deletion must decrement a reference rather than unlink the file — otherwise one user's deletion breaks another user's photo.
6Irreversibility is a property of the architecture, not a policy choice. With no stored credential there is nothing to authenticate a recovery request against, so the usual "contact support" escape hatch does not exist.
