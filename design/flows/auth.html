Flows

Authentication

Sign-in end to end, with the failure branches drawn. Nothing here stores a credential — the ID token is verified, consumed, and discarded, and what persists is only the fact of the identity.

Verifying a token is not the same as decoding one. Every dashed decision below is a check that must actually run: JWKS signature, issuer, audience, expiry, nonce, and a state match against a server-side pending attempt. Skipping any one of them turns delegated authentication into an open door, and a decoded-but-unverified token looks identical to a valid one in a debugger.

Sign-in, first and returning

1There is no separate signup path. The only difference between a first sign-in and a returning one is whether the identity lookup finds a row. Both converge on the same session creation.
2Both failure branches land on the same generic screen. A rejected state, a bad signature, an expired token, and a nonce mismatch are indistinguishable to the user. Telling them apart would also tell an attacker probing the endpoint apart; the real cause goes to the log with a reference ID.
3Facebook diverges at the exchange step. It is not OIDC-conformant and returns no ID token, so the verification box does not apply — it exchanges the code and then calls the Graph API, using the app-scoped ID as the subject.
4Apple diverges at the callback. Its redirect is a form POST rather than a GET, and it returns the user's name only on this first pass through the diagram — never again.

Linking a second provider

5Linking always flows through the already-authenticated account. The user proves control of account A, then adds provider B to it. The reverse — proving B and claiming A — is exactly what makes email-based merging exploitable.
6A refused link changes nothing. The failure screen says so explicitly, because the user's first fear is that something got half-merged.

Session expiry and sign-out

7Sessions are server-side so they can be revoked. A stateless JWT session cannot be invalidated before expiry, which matters more here than usual: the account is the identity, and there is no password to change if something goes wrong.
8Expiry mid-upload preserves the queue. Without that guarantee stated in the message, the reasonable assumption is that a large batch was lost.
